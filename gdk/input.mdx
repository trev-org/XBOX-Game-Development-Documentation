GDK titles read input through **GameInput**, the modern device-agnostic input API for XBOX and Windows.

## Devices

- XBOX Wireless Controllers, Elite, Adaptive Controller.
- Keyboards, mice, racing wheels, arcade sticks, flight sticks.
- Touch (via [Touch Adaptation Kit](/reference/touch-adaptation-kit)) for XBOX Cloud Gaming.

## APIs

- [GameInput](/reference/gameinput) — standard surface.
- [GameInput (extended)](/reference/gameinput-extended) — modern interfaces and the XInput-over-GameInput shim.

## Best practices

- Always handle device hot-plug.
- Re-query inputs on Quick Resume — the active gamepad may have changed.
- Support the XBOX Adaptive Controller for accessibility.
- Read input through a consistent polling cadence; do not mix polled and event-driven reads in the same frame.

## Fundamentals

- **Readings, not events** — GameInput is built around immutable `IGameInputReading` snapshots you fetch on demand. Each reading captures a device's state at a precise timestamp.
- **Versioning** — interfaces are versioned (`IGameInputReading`, `IGameInputReading2`, …). Always ask for the highest version your code understands and fall back gracefully.
- **NuGet packaging** — GameInput on PC ships through a NuGet package independent of the GDK. Stay on a published version your engine has been validated against.
- **No global state** — the GameInput device collection is process-scoped; multiple subsystems can each create their own `IGameInput` instance safely.

## Devices and hardware

| Device class | Notes |
| --- | --- |
| Gamepads | XBOX Wireless, Elite Series 2, Adaptive Controller — full feature set |
| Racing wheels | Force feedback, paddle shifters, H-pattern shifters, handbrake |
| Arcade sticks | Treated as digital gamepads; button-mapping helpers available |
| Flight sticks | Throttle, rudder, hat switches |
| Keyboard / mouse | Per-key state and high-precision motion deltas |
| Touch | Surfaced through GameInput on streaming clients and Windows touch devices |
| Sensors | Accelerometer, gyroscope, light sensor where present |

### Force feedback and haptics

GameInput exposes two haptic models:

- **Rumble motors** — classic low/high-frequency motors on standard gamepads
- **Force feedback** — full effect-graph model (constant, ramp, periodic, spring, damper, friction, inertia) on wheels and flight sticks
- **Trigger haptics** — XBOX Wireless Controller trigger rumble for tactile feedback on shoulder pulls

Always check device capabilities before authoring an effect; not every controller supports every effect type.

### Hardware mapping and interfaces

- **`IGameInputDevice`** — the physical device, capabilities, and metadata (HID IDs, display name, battery state)
- **Logical mapping** — abstract a gamepad's buttons into engine actions; never bind to physical scan codes
- **HID pass-through** — for niche peripherals you can read raw HID reports while still benefiting from device hot-plug and ownership

### Sensors

Read accelerometer and gyroscope deltas through GameInput on controllers that expose them. Pair with the gamepad reading on the same timestamp to do motion-aim or tilt-steering.

## Advanced patterns

- **Callbacks** — `RegisterDeviceCallback` and `RegisterReadingCallback` deliver hot-plug and state-change notifications without polling
- **Work queues** — drive GameInput callbacks onto your own `XTaskQueue` so input does not block on the system thread pool
- **Synchronization** — readings carry monotonic timestamps; use them to align input with simulation and render frames
- **Keyboard and mouse** — read full-key state, repeat-rate awareness, and raw mouse deltas without WM\_INPUT plumbing
- **Virtual keyboard support** — show the on-screen TTY keyboard on console and streaming clients via `XGameUiShowTextEntryAsync`

## Porting from XInput / WGI

- **XInput-on-GameInput shim** — link the GDK's XInput compatibility layer so legacy `XInputGetState` code keeps working while you migrate
- **Windows.Gaming.Input (WGI) port** — direct mapping of WGI concepts (Gamepad, RawGameController) onto `IGameInputDevice` and `IGameInputReading`
- **What to port first** — replace XInput device enumeration and hot-plug, then state polling, then haptics; defer keyboard/mouse and racing wheel work until the gamepad path is solid
