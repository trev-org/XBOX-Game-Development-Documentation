A key component of the Xbox One audio system is the **Scalable Hardware Audio Processing Engine (SHAPE)**. SHAPE:

- Efficiently performs commonly used audio functions via fixed-function hardware blocks: XMA, Sample Rate Convertor (SRC), Equalizer/Compressor (EQ/COMP), and Filter/Volume (FLT/VOL)
- Provides a programmable, embedded **Audio Control Processor (ACP)** to drive those blocks
- Uses **DMA** for system memory access and internal **mix buffers** to minimize traffic on the main memory bus

<Note>
  Many titles never touch SHAPE directly — XAudio2 and audio middleware implement SHAPE components implicitly. Building flowgraphs yourself gives maximum flexibility and access to the acceleration capabilities.
</Note>

SHAPE blocks are driven by two elements:

- **Contexts** — state stored in main memory, generated by the CPU and updatable by CPU or ACP. Read into SHAPE per audio frame. With 128-sample frames at 48 kHz, contexts swap at 375 Hz per channel.
- **Execution list (flowgraph)** — meta commands processed by the ACP; specifies inputs, outputs, and mix-buffer routing. See [ACP overview](/gdk/audio/acp).

## Blocks and capabilities

### DMA

The DMA system supports read/write with automatic float↔integer conversion. It uses circular buffers of de-interleaved 128-sample blocks. One audio frame transfers at a time. Multichannel streams require **one DMA context per channel**.

Buffer sizing:

```cpp
fullBufferSizeInBytes = 128 * 4 * numChannels * numFrames;

readPointer  = (readPointer  + 1) % numFrames;
writePointer = (writePointer + 1) % numFrames;

readAddress  = audioBuffer + (128 * 4 * ((readPointer  * numChannels) + channel));
writeAddress = audioBuffer + (128 * 4 * ((writePointer * numChannels) + channel));
```

<Warning>
  Hardware↔software transitions incur a **2.66 ms** latency. When synchronizing critical code across multiple transitions, consider a CPU-clock delay and latency-tolerant submixes to reduce CPU use.
</Warning>

### XMA

XMA supports mono, stereo, and interleaved multichannel with variable bit rates. On Xbox One vs Xbox 360:

- ~40% increase in pitch-shift capability from the higher clock rate
- Voice count raised from 320 to **512**

Five bits per XMA context track how much decoded PCM remains unconsumed — the SRC can lock context without reading main memory.

<Note>
  xWMA is **not** supported by SHAPE, but is supported via `XAudio2`.
</Note>

### PCM

Linear PCM up to 7.1 at 48 kHz (ACP downmixes for smaller endpoints). S/PDIF output supported. Linear and circular PCM buffers support 16-bit mono/stereo integers, 32-bit mono floats, or 32-bit mono integers (24-bit left-justified or 32-bit with lower 8 bits masked off).

### Sample Rate Convertor (SRC)

Reads 32-bit floating-point PCM or 16/24/32-bit fixed-point PCM from memory (or the XMA decoder output). Operates in mono or stereo. Input rate up to **384 kHz minus epsilon**; output is a fixed **48 kHz**.

- Up to **512 channels** of SRC per audio frame (any mix of mono/stereo)
- Linear and polyphase interpolation
- Resampling range **1:16** (four octaves down) to **3.99:1** (nearly two octaves up)

### Equalization and compression (EQ/COMP)

Contains a three-band programmable equalizer and a dynamic-range compressor in series.

- **Compressor** — monitors input level and creates a dynamic gain multiplier. Applies only above a threshold; ratio (e.g. 2:1) sets attenuation above threshold. `attack` and `release` in milliseconds control response speed (linear or log). _Makeup gain_ is a static value that lifts the signal back into a usable range. `RMS` mode averages over the previous 128 samples.
- **EQ** — three cascaded biquad filters with fully programmable 24-bit coefficients, coefficient range ±7.998, frequency range 20 Hz to 18 kHz, gain range −18 dB to \+18 dB.

Biquad equation:

```text
y[n] = (b0/a0)*x[n] + (b1/a0)*x[n-1] + (b2/a0)*x[n-2] - (a1/a0)*y[n-1] - (a2/a0)*y[n-2]
```

### Filter / volume (FLTVOL)

Used to:

- Model occlusion of sound going around or through objects
- Distribute energy across speakers to model direction of arrival

Takes one channel from a mix buffer, filters and volume-scales it, and writes the output to a mix buffer. Multiple FLTVOL blocks generate one-in / multi-out pans (e.g. surround pans and reverb sends). Implemented as a **Chamberlin filter** with high-pass, low-pass, band-pass modes and variable Q:

```text
f := 2*Sin( ( PI * FC )/FS)
q := 1/Q            // Q ranges from .5 to 5
```

Optional **headroom** scaling (0/1/2/3 bits right-shift) prevents saturation from resonances. If original source is 16-bit (e.g. XMA), max headroom is safe.

Up to **2560 FLTVOL contexts per audio frame**. Filtering behavior is identical to `XAudio2`.

### Mix buffers

Three purposes:

1. Final mixing destination per speaker output (system or per-player)
2. Temporary storage passing between hardware blocks
3. Bridge to main memory via DMA in both directions

Up to **8192 concurrent virtual mix buffers** rendering to **128 physical channels**. Mixing uses hardware accumulators — no DMA required. Supports metering and clipping.

## Overflow, magnitude, and saturation

Each block other than SRC maintains an **internal saturation flag**. Each hardware block also maintains two four-bit peak-magnitude values (persistent peak, plus per-frame peak) computed by counting leading zeros of the peak's absolute value. Mix buffers maintain their own pair of peak-magnitude values after accumulation.

| Binary value | Meaning |
| --- | --- |
| `B'0000` | **Saturation** — an output exceeded signed 24-bit range and was clamped to ±8,388,607 |
| `B'0001` | Absolute peak \> MAX \>\> 1 |
| `B'0010` | Absolute peak \> MAX \>\> 2 |
| `B'0011` | Absolute peak \> MAX \>\> 3 |
| `B'0100` | Absolute peak \> MAX \>\> 4 |
| `B'0101` | Absolute peak \> MAX \>\> 5 |
| `B'0110`–`B'1101` | Absolute peak \> MAX \>\> 6 to 13 |
| `B'1110` | Absolute peak \> MAX \>\> 14 |
| `B'1111` | Absolute peak ≤ MAX \>\> 14 |

A 0- to 7-bit right shift on the output of any block (prior to accumulation into the destination mix buffer) helps avoid overflow.

## SHAPE queues

Two queues reduce hardware/app interlocks:

- **Command and Control Queue (CCQ)** — CPU→ACP commands executed once (typically at frame end). Used to update contexts, supply new XMA bit-stream data, or point at a new execution list.
- **Status and Reporting Queue (SRQ)** — ACP→CPU events that don't require real-time response: bit-stream buffer consumption, errors/warnings/flags, debug/perf data.

## Programming

Program SHAPE directly through the `IACPHAL` interface. The GDK ships utility methods, structures, enumerations, and their source — in your project include only `acphal.h`; it references all utility headers. All utility functions honor the `NO_SHAPE_CONTEXT_VALIDATION` macro — define it for final retail builds to skip validation.

For sharing SHAPE and XMA resources with `XAudio2`, see the Remarks section of [`XAudio2Create`](https://learn.microsoft.com/windows/desktop/api/xaudio2/nf-xaudio2-xaudio2create).

Full utility method documentation: [ACP overview](/gdk/audio/acp).

## Persistent vs non-persistent flowgraphs

**Persistent** flowgraphs remain resident and repeat processing each frame after read/write pointers advance. Use for:

- Highly complex flowgraphs that would be expensive to reassemble each frame
- Highly static flowgraphs with unchanging voice topology

**Non-persistent** flowgraphs are consumed once. Use for:

- Frequently changing voice topologies
- Audio engines whose processing cadence isn't a multiple of 2.667 ms
- Faster-than-real-time audio processing

## Debugging

Register for messages via the `NumMessages` parameter of [`IAcpHal::Connect`](https://learn.microsoft.com/en-us/gaming/gdk/_content/gc/reference/audio/acphal). Verify success by observing `ACP_MESSAGE_TYPE_FLOWGRAPH_COMPLETED` for each submitted flowgraph before shipping.

<AccordionGroup>
  <Accordion title="Missed messages">
    Examine `ACP_MESSAGE::droppedMessageCount`. Non-zero means the queue was full — service faster or make the queue larger.
  </Accordion>

  <Accordion title="Frame-outs">
    A flowgraph that can't finish before the 2.667 ms frame ends produces `ACP_FLOWGRAPH_TERMINATED_TIME_EXCEEDED` on persistent flowgraphs (which are then incomplete). Non-persistent flowgraphs are not constrained and run until complete, even across frames.
  </Accordion>

  <Accordion title="Blocked commands">
    SRC and DMA commands may be reported as blocked (`ACP_MESSAGE_TYPE_SRC_BLOCKED`, `ACP_MESSAGE_TYPE_DMA_BLOCKED`):

    | Command type | Blocking scenario |
    | --- | --- |
    | XMA SRC | Associated XMA context has a parser error or no source data. XMA SRC will **not** block due to a lack of decoded data. |
    | PCM SRC | Associated PCM context is `SHAPE_PCM_MODE_CIRCULAR` and has no source data. |
    | Read (DMA from mix buffer) | DMA buffer is full. |
    | Write (DMA to mix buffer) | DMA buffer is empty. |

    Blocked commands are evicted from the graph and can cause dropped audio. Prevent DMA blocking with a sufficiently large audio buffer double-buffered against your streaming interval.

    **SRC command modes:**

    - `SHAPE_SRC_COMMAND_TYPE_START` — used for nearly all SRC commands; expect more audio data.
    - `SHAPE_SRC_COMMAND_TYPE_STOP_IMMEDIATE` — stops immediately; SRC outputs a zeroed buffer for this frame.
    - `SHAPE_SRC_COMMAND_TYPE_STOP_END` — marks the last packet of a voice. **If the last packet isn't submitted with `STOP_END` or `STOP_IMMEDIATE`, the SRC command never completes and stalls the flowgraph.**
  </Accordion>

  <Accordion title="Synchronization">
    Don't modify a context structure while it's in use. `SubmitCommand` can schedule commands at a specific frame, at the beginning of the next frame, or ASAP.

    <Note>
      _ASAP_ is still asynchronous from title CPU processing. Some commands don't complete immediately (e.g. context in the middle of a non-interruptible op). Wait for `ACP_MESSAGE_TYPE_COMMAND_COMPLETED` to confirm processing.
    </Note>

    See also [Getting into SHAPE: best practices for flowgraph construction](/gdk/audio/best-practices-flowgraph).
  </Accordion>
</AccordionGroup>
