The Microsoft Game Development Kit (GDK) includes APIs for broadcast notifications and UI, adding metadata to screenshots, video clips, and broadcasts, and capturing diagnostic screenshots and video. Broadcast notifications provide insight into the broadcasting pipeline. Broadcasting UI puts the user in control of starting and stopping a broadcast. Metadata makes it easier to search recordings — for example, adding the name of a map, a level, or anything about the specific moment captured. Together these APIs give you better control and insight over your screenshots, video clips, and broadcast.

## Broadcasting notifications and UI

Use the `XAppBroadcast*` APIs to detect broadcast state and hand off to the shell UI:

| API | Purpose |
| --- | --- |
| `XAppBroadcastGetStatus` | Retrieve status updates on the state of broadcasting. Use this to determine whether a broadcast **can** start. |
| `XAppBroadcastShowUI` | Show the broadcast UI for the current user. The user then manually initiates the broadcast. |
| `XAppBroadcastIsAppBroadcasting` | Determine whether the current app is currently broadcasting. |
| `XAppBroadcastUnregisterIsAppBroadcasting` | Unregister from broadcast-status change events. |

Many factors go into determining whether a broadcast can start: capture resource availability, whether the game allows broadcasting, and whether the user or system has disabled broadcasting.

<Tip>
  If all members of the `XAppBroadcastStatus` struct (besides `canStartBroadcast`) return `false`, then `canStartBroadcast` returns `true` — the broadcast is ready to launch.
</Tip>

## Adding metadata to screenshots, clips, and broadcasts

Several APIs add and manage metadata attached to a screenshot, video clip, or broadcast. Adding metadata is optional, but it makes it easier for a user to find the recording they want. Metadata items can be strings, integers, or doubles.

The system allocates storage space for metadata items. If the allocated space runs low, `AppCaptureMetadataPriority` determines the relative priority of stored items and the order in which metadata is purged to free space.

## Voice chat

<Warning>
  Voice chat should be considered **user-generated content** and can contain personally identifiable information or other potentially sensitive data. A user's rendered voice in game chat should **never** be included in any recorded clips or game captures.
</Warning>

Exclude voice from captures by assigning the proper audio category to the render stream that contains the user's voice: `AudioCategory_GameChat`. Tagging the stream this way signals the system to ignore it when capturing for Game DVR clips.

See [Audio](/gdk/audio/overview) for the WASAPI/XAudio2 integration pattern.

## Diagnostic screenshots and video clips

With the GDK diagnostic APIs you can capture screenshots and video clips for debugging and diagnostics.

<Note>
  Diagnostic capture APIs are available **only on Development Kits**. Calling them on a retail console results in an immediate failure.
</Note>

Diagnostic captures behave differently from user-facing captures:

- Captured screenshots and video clips go to the **local game partition**, not to the usual user storage.
- If the game is running in high dynamic range (HDR), the caller can specify whether to capture an **SDR** screenshot, an **HDR** screenshot, or **both**.
- After a screenshot is recorded, the resulting struct contains path information for the screenshot files.
- Depending on the user's Game DVR setting, video clips can be returned as either **H.264 (AVC)** or **H.265 (HEVC)** encoded video.
- The video result struct also includes start time, duration, width, and height.

## Normal screenshots

The GDK also supports capturing **normal** screenshots (the same as a user-initiated screenshot):

- Resulting screenshots are stored in the normal user storage for screenshots.
- The system displays a notification confirming that a screenshot was captured.
- Because screenshots are stored in a separate partition that isn't directly accessible from the game partition, you must use the provided **open / read / close stream APIs** to access the recorded screenshots.
- If the game is running in HDR, the paths for both the **SDR** and **HDR** versions of the screenshot are returned.
