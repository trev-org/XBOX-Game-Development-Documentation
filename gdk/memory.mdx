XBOX Series X|S exposes a unified GPU \+ CPU memory model with strict per-title budgets. Manage memory explicitly to hit those budgets.

## Key concepts

- **Title budget** — fixed per generation (Series X, Series S, XBOX One).
- **GPU upload heap vs default heap** — choose carefully; default heaps are GPU-local and faster.
- **D3D12 placed resources** — explicit heap management.
- **Memory hooks** — the GDK accepts user-provided memory allocators for XAsync, XCurl, libHttpClient, XSAPI, and PlayFab.

## Best practices

- Pre-budget per subsystem (rendering, audio, gameplay, networking, scripting).
- Track allocations with PIX events.
- Run with low-memory simulation to verify graceful degradation.

## GDK memory manager

The GDK ships a purpose-built memory manager (`XMem`) that game code uses for all general allocation. It tracks every allocation, categorises it for diagnostics, and lets you swap in your own backing allocator without changing call sites.

- **Tags** — every allocation carries a numeric tag (mesh, texture, audio, AI). Use tags for budget tracking and leak hunting.
- **Allocator hooks** — the GDK accepts user-provided allocator callbacks for XAsync, XCurl, libHttpClient, XSAPI, PlayFab, and your own subsystems.
- **Address-space management** — request large contiguous reservations explicitly; the manager surfaces fragmentation before it becomes a crash.

## Virtual memory allocator

For very large allocations or systems that need explicit address-space control (DirectStorage staging buffers, custom paging), use the GDK **virtual memory allocator**:

- `VirtualAlloc`-style reserve / commit semantics
- Page-aligned, with explicit control over read / write / execute flags
- Pair with `XMemSetAllocationContext` so reserved ranges show up correctly in diagnostics

## Writeable memory-mapped files

The GDK supports writeable memory-mapped files for streaming and content authoring scenarios. Use them for:

- Tools and editors that need OS-level coherence between an on-disk file and an in-memory view
- Content authoring scenarios where the file is the source of truth and the in-memory view is an editing window
- Avoid for runtime game data: regular `XGameSave` or DirectStorage flows are simpler and faster

## Cross-core memory costs

CPU cores on XBOX Series X|S share L3 cache and a unified memory bus, but cross-core fences and dirty cache-line transfers still cost real time:

- Producer/consumer queues should pin to a fixed core pair where possible
- Avoid sharing mutable state across more than two cores on the hot path
- Use `XThreadGetCurrentProcessorNumber` and core-affinity APIs to keep small hot allocations in core-local caches
- The cost of a single cross-core cache transfer is documented and varies between Series S, Series X, and Xbox One — profile before refactoring

## Kernel memory usage

A portion of physical memory is reserved for the kernel and platform services. Things to know:

- The kernel reservation varies by SKU and OS version; do not hard-code title budgets
- Some platform services (Game DVR, voice chat, broadcast) grow the kernel working set when active — keep headroom
- Use `XMemGetAllocationStatistics` and the dev kit memory tooling to monitor kernel \+ title totals together

## Diagnostics and tracking

- **PIX timing capture** — visualise allocations on the timing track
- **`XMem` diagnostics** — per-tag totals, peak high-water mark, allocation count, fragmentation
- **Low-memory simulation** — run with a reduced budget to verify graceful degradation paths
- **Leak detection** — `XMemSetAllocationContext` to attribute allocations to a subsystem; flush the report at scene boundaries

## Porting to the GDK memory manager

When migrating an XDK or PC title:

1. Wrap all heap entry points (`new`, `malloc`, `HeapAlloc`) with `XMem` shims so every allocation is categorised
2. Pass GDK allocator callbacks to XSAPI, PlayFab, XCurl, and libHttpClient at init time
3. Sweep for direct `VirtualAlloc` calls and route through the GDK virtual memory allocator
4. Re-baseline budgets on the new memory manager — overhead and alignment differ from the legacy XDK heap

## Tooling and configuration

- **Dev kit memory budgets** — configurable per-build via the dev kit's memory tooling so you can validate Series S budgets on a Series X dev kit
- **Title budgets** — set per-SKU in your build configuration; CI should fail builds that exceed the budget for any SKU
- **In-game overlay** — toggle the dev memory overlay from Dev Home for live per-tag totals
