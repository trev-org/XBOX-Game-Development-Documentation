This article explains the container-and-blob model and covers provider initialization, provider closure, and the update-handle lifecycle. It outlines atomic update behavior with sync-flow diagrams, file-size and quota constraints, best practices, and FAQs.

The `XGameSave` API enables you to manage blobs and containers for Game Saves data.

<Note>
  We recommend [XGameSaveFiles](/gdk/xgamesavefiles) for Game Saves in GDK titles. Use `XGameSave` only if `XGameSaveFiles` isn't an option.
</Note>

## Terminology

| Term | Definition |
| --- | --- |
| **Lock** | A mechanism that grants exclusive access to a title's Game Saves for a specific user on the device they're actively using. Ensures no other device can modify the Game Saves while the lock is held. |
| **Provider** | The intermediary process that communicates with the Game Save system and manages the title's data and the user's lock. |
| **Container** | Analogous to a folder. |
| **Blob** | Analogous to an individual file. |

## Provider management

To acquire a storage space, the game must initialize a provider. After connection, the title tries to acquire a lock to the title's cloud storage by calling `XGameSaveInitializeProvider` or `XGameSaveInitializeProviderAsync`.

If the title fails to sync from the cloud because of connection loss, determine whether users can continue playing in offline mode.

The title must close the provider with `XGameSaveCloseProvider` when it suspends or terminates. The provider can't be reused across suspend/resume boundaries.

<Note>
  This applies only to `XGameSave`. `XGameSaveFiles` automatically closes the provider.
</Note>

## Container management

To avoid data loss when accessing containers (like creating containers before syncing completes), call `XGameSaveEnumerateContainerInfo` or `XGameSaveEnumerateContainerInfoByName` to view the containers a user has.

- `XGameSaveCreateContainer` — Gets a container handle to a new or existing container. Creates the container if it doesn't exist.
- `XGameSaveDeleteContainer` — Deletes a container. All blobs within are also deleted.
- `XGameSaveCloseContainer` — Closes container handles when no longer in use or when the title suspends/terminates. Prevents handle leaks.

## Blob management

Manipulating data within a container is done by calling `XGameSaveCreateUpdate`.

Update rules:

- An update applies to one container.
- An update can write at most `GS_MAX_BLOB_SIZE` (16 MB).
- Multiple blobs can be modified in a single update.
- A single blob can only have one modification per update.
- Submitting an update consumes the `XGameSaveUpdate` handle. Close it whether the submit succeeded or failed.
- Updates are atomic. If any part fails, the entire update fails.

Update APIs:

| API | Purpose |
| --- | --- |
| `XGameSaveCreateUpdate` | Creates an update context to store blob modifications. |
| `XGameSaveSubmitBlobWrite` | Writes data to a new or existing blob (requires an update context). |
| `XGameSaveSubmitBlobDelete` | Deletes a blob. |
| `XGameSaveSubmitUpdate` | Submits the update context. |
| `XGameSaveCloseUpdate` | Closes the update handle. Call after every submit to prevent leaks. |
| `XGameSaveEnumerateBlobInfo` / `XGameSaveEnumerateBlobInfoByName` | Access all blobs in a container. |

<Note>
  Data written to blobs is represented as Base64 when exported to XML.
</Note>

## Game Saves flow

<Frame>
  ![Flowchart of the simplified Game Saves sync process.](/images/simple-sync-overview.png)
</Frame>

### Title start

Title start occurs when the user launches or resumes the title.

### User sign-in

The title initiates user sign-in. This is also where you invoke `XGameSaveInitializeProvider`. See [User models](/gdk/game-saves-developer-guide#user-models).

### Connection check

The title determines whether it can connect to the Xbox network. If it can't, it's up to you to enable [offline mode](/gdk/game-saves-syncing#connection-check).

### Data ownership check

The device checks whether the user is currently playing on other devices. Only one device at a time can access the user's data for a specific title.

### Syncing data with the cloud

The device syncs local storage data with the cloud. If there's a conflict, the system prompts the user with [Which one do you want to use?](/gdk/game-saves-dialogues#which-one-do-you-want-to-use).

### Gameplay loop

The title is freely able to read and write to Game Saves local storage.

### Game session end

When the game session ends, the system automatically attempts to upload data. Ensure your title calls `XGameSaveUninitializeProvider` during its exit flow to avoid leaving a provider initialized.

For detailed sync information, see [Understanding the Game Saves sync flow](/gdk/game-saves-syncing).

## Limits and quotas

### Limits

`XGameSaveUpdate` limits each update to **16 MB**. `XGameSave` can only manage individual file updates up to 16 MB. This differs from `XGameSaveFiles`, which supports files up to 64 MB.

### Quotas

The maximum data a user can save per title is **256 MB**. Use `XGameSaveGetRemainingQuota` to get the remaining quota. Contact your Developer Partner Manager (DPM) for a storage extension.

## Best practices

- Don't save data and then immediately query and ask for the same data back.
- Data dependencies across containers aren't reliable. Each `XGameSaveSubmitUpdate` call applies all changes atomically or not at all.
- The more blobs you use per update call, the more time is required to complete the atomic file-system operations.

## FAQs

<AccordionGroup>
  <Accordion title="I'm upgrading my Game Saves implementation. What is the correct approach?">
    Use [XGameSaveFiles](/gdk/xgamesavefiles).
  </Accordion>

  <Accordion title="Can I use XGameSave with XGameSaveFiles?">
    Yes, but only for migrations. See [Interop between XGameSave and XGameSaveFiles](/gdk/game-saves-walkthroughs#interop-between-xgamesave-and-xgamesavefiles).
  </Accordion>

  <Accordion title="What file path does XGameSave save to?">
    - **Console:** A temporary path is provided while the title is active. Console files can't be accessed via File Explorer.
    - **PC:** `%AppData%\Local\Packages\<PACKAGE_NAME>\SystemAppData\wgs\<HexXuid>_<SCID>\`

    The PC path for `XGameSave` uses `wgs`; `XGameSaveFiles` uses `xgs`.
  </Accordion>

  <Accordion title="Can I specify the path where data should be saved?">
    Yes, but only for PC. Recommended only if porting from another title. Uses [no-code cloud saves](/gdk/game-saves-walkthroughs#porting-previous-titles-to-pc-game-saves-with-no-code-cloud-saves).
  </Accordion>

  <Accordion title="Is there a situation where I ever use Sync on Demand?">
    No. It's there for legacy support reasons.
  </Accordion>
</AccordionGroup>
