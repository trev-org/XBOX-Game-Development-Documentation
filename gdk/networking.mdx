Networking on XBOX console is not a free-for-all: the GDK restricts which socket APIs you may use, mandates specific security behaviors, and requires your title to integrate with XBOX network security to pass certification. Understanding these requirements early in your networking design will save you significant rework before submission.

<Warning>
  Using unapproved networking APIs or bypassing XBOX network security requirements will cause your title to **fail certification**. Review the requirements in this page and the linked GDK networking documentation before writing any network code.
</Warning>

## GDK networking requirements

The GDK permits titles to use the following socket APIs:

- **WinSock 2** (`winsock2.h`) — the standard Berkeley-style socket API on Windows and XBOX.
- **GDK-specific networking extensions** — additional APIs that expose XBOX network security features.

You must **not** use raw IP sockets to bypass the XBOX security layer, and you must not use deprecated XDK APIs in GDK titles.

<Note>
  Detailed networking documentation, including the full list of approved APIs, socket option requirements, and advanced QoS configuration, is in the NDA-gated [GDK Networking section](https://learn.microsoft.com/en-us/gaming/gdk/docs/features/console/networking/gc-networking-toc). Sign in with your authorized Partner Center account to access it.
</Note>

## WinSock support

WinSock 2 is fully supported in GDK titles and behaves largely the same as on Windows PC. Standard socket operations — `socket`, `bind`, `connect`, `send`, `recv`, `select` — all work as expected.

```cpp
#include <winsock2.h>
#include <ws2tcpip.h>

// Initialize WinSock
WSADATA wsaData;
int result = WSAStartup(MAKEWORD(2, 2), &wsaData);
if (result != 0) { /* handle error */ }

// Create a UDP socket
SOCKET sock = socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP);
if (sock == INVALID_SOCKET) { /* handle error */ }

// ... use sock for your networking ...

closesocket(sock);
WSACleanup();
```

<Tip>
  Always call `WSAStartup` with version 2.2. GDK titles require WinSock 2.2 and must call `WSACleanup` before exiting to avoid resource leaks.
</Tip>

## XBOX network security requirements

All network traffic sent between players in an XBOX title must pass through the **XBOX network security layer**. This layer provides:

- **Encryption** — all peer traffic is encrypted in transit.
- **Authentication** — the XBOX identity of each endpoint is verified using the player's signed-in XBOX account.
- **Anti-cheat** — the security layer prevents spoofed sender addresses and man-in-the-middle attacks.

You integrate with XBOX network security by using the **secure sockets** APIs provided in the GDK. These APIs wrap your underlying WinSock sockets with the XBOX security layer transparently. You should not implement your own encryption layer on top of XBOX secure sockets, as this can interfere with the security model and is not required.

Titles that pass raw, unencrypted game traffic directly between players — bypassing secure sockets — will fail certification with a network security XR violation.

## PlayFab Party (recommended P2P/relay solution)

For most titles that need peer-to-peer networking, Microsoft recommends **Azure PlayFab Party**. Party is a cross-platform library that handles:

- **Relay networking** — traffic routes through Azure relay servers so players never need to expose their IP addresses.
- **NAT traversal** — Party negotiates connections through NATs automatically.
- **Voice and text chat** — integrated chat channel with automatic accessibility features (speech-to-text, text-to-speech).
- **Cross-platform play** — the same Party library works on XBOX, Windows PC, PlayStation, Nintendo Switch, iOS, and Android.

Party satisfies XBOX network security requirements on XBOX and Windows PC when used correctly. It replaces the deprecated **XBOX Integrated Multiplayer (XIM)** service, which does not work in GDK titles.

```cpp
// Minimal PlayFab Party initialization sketch
#include <Party.h>

using namespace Party;

PartyManager& manager = PartyManager::GetSingleton();

// Initialize with your PlayFab title ID
PartyString titleId = "YOUR_PLAYFAB_TITLE_ID";
PARTY_HANDLE handle = nullptr;
PartyError err = manager.Initialize(titleId);
if (PARTY_FAILED(err)) { /* handle error */ }

// Create a local user from the signed-in XBOX user's entity token
// (obtain entityToken from PlayFab authentication flow)
PartyLocalUser* localUser = nullptr;
err = manager.CreateLocalUser(
    "PLAYFAB_ENTITY_ID",
    "PLAYFAB_ENTITY_TOKEN",
    &localUser
);
```

<Note>
  Integrating PlayFab Party requires a PlayFab account and a title configuration in the PlayFab Game Manager. See the [Party overview](https://learn.microsoft.com/en-us/gaming/playfab/features/multiplayer/networking/) and the [XBOX and PC multiplayer design guidance](https://learn.microsoft.com/en-us/gaming/gdk/docs/services/multiplayer/overviews/multiplayer-design-guidance-xbox-pc-gdk) for the full integration path.
</Note>

## Networking and multiplayer session management

Network connectivity alone is not enough for a compliant XBOX multiplayer experience. You also need to integrate with XBOX services for:

- **Session lifecycle** — use Multiplayer Session Directory (MPSD) or Multiplayer Manager (MPM) to manage player sessions.
- **Invites and joins** — players must be able to invite friends and join from the XBOX shell using the standard invite flow.
- **Multiplayer Activity (MPA)** — required for titles using custom matchmaking to surface join-in-progress to the XBOX shell.

See the [Multiplayer](/services/multiplayer) page for a full breakdown of these requirements.

## Key APIs summary

| API | Purpose |
| --- | --- |
| `WSAStartup` / `WSACleanup` | Initialize and tear down the WinSock runtime |
| `socket` / `bind` / `connect` | Standard WinSock socket lifecycle |
| `send` / `recv` / `sendto` / `recvfrom` | Standard data transfer |
| GDK secure socket APIs | Wrap sockets with XBOX network security (see NDA docs) |
| `PartyManager::Initialize` | Initialize PlayFab Party |
| `PartyManager::CreateLocalUser` | Register a signed-in player with Party |
| `PartyNetwork::ConnectToNetwork` | Join or create a Party network |

## QoS packet tagging

Tag latency-sensitive outbound traffic (gameplay updates, voice) with DSCP/QoS markers so that the console network stack and home routers can prioritize them over background traffic. The GDK exposes per-socket QoS APIs; tag once at socket creation and avoid hot-path retagging.

## Reserved ports and firewall exceptions

A range of XBOX-system ports is reserved for platform services (Live, Party, system telemetry) and cannot be bound by titles. Ship a list of game-specific UDP/TCP ports in your packaging metadata so the console firewall can open them automatically — do not assume players will configure their home routers.

## HTTP stacks: xCurl and WinHTTP

- **xCurl** — libcurl-compatible HTTP client recommended for GDK titles. Cross-platform, supports HTTP/2, easy to plug into existing engines that already speak libcurl.
- **WinHTTP** — Windows-native HTTP client, also available on XBOX. Pick WinHTTP when you already depend on it for tooling/services parity.
- Custom HTTP stacks are allowed but must be debuggable through the standard platform network capture tooling.

## XDK migration

Titles porting from XBOX One ERA (XDK) replace XDK-era socket and HTTP APIs with WinSock \+ xCurl/WinHTTP. The migration guide maps every XDK web-request and game-mesh API to its GDK equivalent.

## MsQuic (QUIC / HTTP/3) for low-latency game mesh

**MsQuic** is the Microsoft implementation of the QUIC transport protocol. The GDK supports MsQuic for game traffic that needs the latency of UDP with the reliability and security of TLS:

- 0-RTT reconnection for fast resume after network blips
- Stream multiplexing without head-of-line blocking (key for mixed gameplay \+ chat traffic)
- Built-in TLS 1.3 — works with the XBOX secure sockets layer for peer authentication
- Suitable for dedicated-server titles that want HTTP/3-style transport without writing their own UDP reliability

Use MsQuic when PlayFab Party's relay model adds too much latency for your title and you control your own backend.

## WinSock and connectivity initialization

GDK networking has a defined startup contract:

1. Call `XNetworkingGetConnectivityHint` to read the platform's view of network availability before initializing your stack
2. Call `WSAStartup(MAKEWORD(2, 2), ...)` and check the returned data
3. Register for connectivity-changed notifications so you can fail multiplayer gracefully when the link drops
4. On shutdown, terminate per-socket activity, then `WSACleanup`

Skipping the connectivity hint causes mysterious failures on first launch after a sign-in change; the platform may not yet have a fully resolved network when your title starts.

## Preferred local UDP multiplayer port

For LAN play and direct-connect scenarios:

- Reserve a single UDP port via your `MicrosoftGame.config` `<NetworkManifest>` so the platform firewall opens it automatically
- Use it as your title's well-known port for LAN discovery
- Fall back to a random ephemeral port if the well-known port is in use — never crash on bind failure

## Game mesh integration recipes

| Stack | When to use |
| --- | --- |
| **PlayFab Party** | Default for cross-platform peer-to-peer and chat — handles relay, NAT traversal, and voice in one library |
| **MsQuic** | Custom client-server with low latency and built-in encryption |
| **WinSock UDP \+ secure sockets** | Bespoke peer-to-peer where you control the reliability layer |
| **WinHTTP / xCurl** | REST/JSON service calls; matchmaking glue; analytics ingestion |

### Party Unity plug-in

PlayFab Party ships a **Unity plug-in** that wires Party into Unity titles with C# bindings:

- Drop-in component for local player onboarding
- Networking and chat callbacks exposed as Unity events
- Built-in voice activity / transcription hooks for accessibility
- Works on XBOX, PC, mobile, and other Party-supported platforms

### Party Unreal Online Subsystem

For Unreal titles, an **OnlineSubsystem** implementation backs the standard `IOnlineSubsystem` interface with Party:

- Sessions, voice, friends, and presence flow through Unreal's existing OSS API
- Lets engine and gameplay code stay platform-agnostic while Party handles connection state
- Use alongside the GDK OnlineSubsystem for XBOX services identity and entitlement plumbing

### PC port behavior

PlayFab Party and the GDK secure sockets layer behave slightly differently on PC vs console:

- On PC, the security layer still requires a signed-in MSA, but uses the local Windows firewall rather than the platform firewall
- Some XBOX-only features (e.g. group chat with off-network players, party-wide invites from the shell) require a signed-in Live account on PC
- Test the PC build with the Windows firewall in default state; never disable it as part of your QA matrix

## Networking tools

The GDK ships several diagnostic tools you should integrate into your QA pipeline:

| Tool | Purpose |
| --- | --- |
| **NetCap** | On-device packet capture for game traffic — replaces Wireshark on the console; capture and replay sessions for repro |
| **NetStress** | Synthetic network impairment — inject latency, jitter, loss, and bandwidth caps without specialised hardware |
| **Fiddler (PC)** | HTTPS proxy for inspecting xCurl / WinHTTP REST traffic in real time |
| **Fiddler setup** | Documented profile for trusting the dev kit / PC certificate root so HTTPS decryption works |
| **GDK connectivity simulator** | Force connectivity-hint changes to validate offline / online transitions |

Bake NetStress profiles into your regression suite — the most common multiplayer bugs only repro under specific latency or loss curves.

## QoS networking deep dive

Beyond DSCP packet tagging, the GDK exposes:

- **QoS probes** — measure round-trip and bandwidth to candidate peers before committing to a session host
- **Bandwidth budgets** — declare per-session bandwidth ceilings so the platform can deprioritise non-game traffic
- **Path MTU discovery** — automatic for WinSock and MsQuic; avoid hard-coding MTU below 1200 bytes
- **Per-stream priorities** (MsQuic) — keep voice and gameplay updates ahead of bulk asset transfers
