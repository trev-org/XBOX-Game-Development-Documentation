The GDK exposes a threading model that gives your title fine control over which threads run frame-critical work and which threads absorb latency for background operations. This page covers the practical rules for structuring threads on XBOX hardware and Windows PC — how to mark threads as time-sensitive, how to distinguish rendering / audio threads from work threads, and how to diagnose the common threading issues that show up in performance captures.

## Time-sensitive threads

A **time-sensitive thread** is one your title has explicitly marked so the OS scheduler prioritizes it and system tooling asserts against accidental blocking calls. Frame-critical threads — render, audio mixdown, physics substep, low-latency input — should always be marked time-sensitive.

Use [`XThreadSetTimeSensitive`](/reference/xthread) on the thread you want to promote, then use `XThreadAssertNotTimeSensitive` inside any function known to block (file I/O, mutex acquisition, network I/O, long-running allocations). During development, those asserts fire the moment a blocking call sneaks into a frame-critical thread — much cheaper to catch than tracking down a stutter in a PIX capture months later.

```cpp
// On the render thread, at startup:
XThreadSetTimeSensitive(true);

// Inside a helper that must never block:
void ReadTexture(const char* path, /* ... */)
{
    XThreadAssertNotTimeSensitive();
    // Do the I/O — will fire the assert if called from a time-sensitive thread.
}
```

Mark render / audio threads time-sensitive **and** design their callers to schedule blocking work onto an [`XTaskQueue`](/reference/xtaskqueue) instead of running it inline.

## Threads and task queues

Most of your background work should not run on its own thread — it should run on the process task queue or a task queue you own. The GDK async pattern is built on `XTaskQueue`, and the port dispatch mode you configure determines whether callbacks fire on the thread pool or on a specific game-loop thread.

See the [async programming model](/gdk/async-programming) and [task queues](/gdk/async-task-queues) for the full pattern. Key rules:

- Do not spin your own `std::thread` for GDK async work — use task queues.
- For time-sensitive threads that also need to drain completions, configure a **manual** completion port and drain it in your game loop.
- Keep the number of raw OS threads small — one per critical work class, not one per system.

## Core utilization patterns

On XBOX consoles the CPU cores are heterogeneous. Some cores are reserved for the system, and the remaining cores are what your title can run on. Two patterns to watch for in profiling captures:

### Idle cores

If a core is idle for large parts of a frame, work is either serialized behind a bottleneck (see [Serialization](#serialization) below) or your job system is not scheduling enough parallel work to fill it. Look for missing parallelism, over-eager locking, or under-utilized job dependencies.

### Spinning cores

A core running hot without producing useful frame progress is usually spinning on a lock or in a busy-wait. Check for:

- Custom spin locks that never yield.
- Third-party middleware that spins waiting for I/O.
- Debug asserts firing inside a tight loop.

Both patterns are easy to spot in a PIX timing capture — see [PIX for XBOX](/tools/pix-for-xbox).

## Floating threads

"Floating threads" are threads that the scheduler moves between cores. On XBOX, uncontrolled float degrades cache locality and can cost frame time. Pin frame-critical threads to specific cores with the standard Win32 affinity APIs, and prefer to run all work for a system on the same core when possible.

## Common threading issues

A short catalog of the issues that most often show up in shipping titles:

### High context switches

When many threads run at similar priority, the scheduler switches between them frequently — each switch costs a few microseconds. If a PIX capture shows thousands of context switches per frame:

- Reduce the number of active threads.
- Prefer task queues over dedicated threads.
- Use `XThreadSetTimeSensitive` on the render / audio threads so they preempt background work cleanly.

### Serialization

Serialization is the pattern where multiple threads that should run in parallel end up waiting on the same lock, queue, or resource. Common causes:

- Global allocator lock (mitigate with per-thread arenas or a lock-free allocator).
- Single log queue writer (batch or shard the log).
- Job system with a single work-stealing queue.

### Threads locking

Deadlocks and priority inversions are catastrophic. Design guidance:

- Never acquire two locks in different orders — use a strict lock hierarchy.
- Never block a time-sensitive thread on a lock owned by a background thread.
- Use lock-free structures for producer/consumer queues between the game loop and worker threads.

## Finding threading issues in captures

PIX for XBOX is the primary tool for diagnosing threading issues. Standard flow:

1. Capture a timing trace covering several frames of the problem scenario.
2. Filter the timeline to your CPU cores — look for gaps (idle) and hot spans (busy).
3. Cross-reference PIX event markers (`PIXBeginEvent` / `PIXEndEvent`) to find the systems responsible for gaps and spikes.
4. If a thread stalls, expand the stack sample at the stall point to see whether it was waiting on a lock or a kernel object.

See [PIX for XBOX](/tools/pix-for-xbox) and the [PIX3 API reference](/reference/pix3) for capture and event-markup details.

## Threading across the GDK

Many GDK APIs have documented threading requirements — the runtime documents whether each call is safe from any thread, must be called from the process main thread, or dispatches its completion on the task queue passed in. When integrating a new module, check its API reference for the threading contract before adding it to your frame loop.

Relevant runtime surfaces to review:

- [`XTaskQueue`](/reference/xtaskqueue) — the primary dispatch primitive.
- [`XAsync`](/reference/xasync) and [`XAsyncProvider`](/reference/xasyncprovider) — how async operations announce completion on the queue.
- [`XThread`](/reference/xthread) — time-sensitive thread management.
