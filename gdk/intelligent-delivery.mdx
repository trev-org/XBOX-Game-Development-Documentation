**Intelligent Delivery** reduces install size by splitting content into chunks and applying rules for when each chunk installs.

## Capabilities

| Capability | Use case |
| --- | --- |
| **Features and recipes** | Independently addable/removable functionality (e.g., campaign vs multiplayer) |
| **Device specifiers** | Tag chunks by device type (e.g., XBOX One X 4K textures) |
| **Language specifiers** | Install only localized assets for the system language |
| **Custom tags** | Group related chunks |
| **OnDemand content** | Deferred install (deprecated — use Features) |

<Warning>
  **ContentType specifiers and OnDemand tags are deprecated** in favor of Features.
</Warning>

<Warning>
  Feature names, recipe names, and custom tag names are **not encrypted** in the package on CDN. Don't use sensitive data in specifier names.
</Warning>

## How recipes work

A **recipe** is the mapping from a device/user state to the set of chunks that should be installed:

- **Language recipe** — install the matching language chunks based on the user's Windows / console language preference
- **Device recipe** — install hardware-specific chunks (4K textures for Series X, lower-fidelity assets for Series S)
- **Features recipe** — install opt-in feature chunks (campaign, raid pack, hi-fi audio) on demand
- **Custom recipe** — author your own mapping for partner-specific scenarios
- **On-demand chunks** — keep optional content out of the initial install and request it at runtime through `XPackageInstallChunks`

Recipes are evaluated at install time and again whenever the user changes a relevant setting (e.g., language) or your title calls a chunk-install API.

## Authoring guidance

- Keep the **first chunk** small enough to boot to a playable state — required for streaming install certification
- Group localized assets per language, not per file — minimises the number of cross-chunk references
- Tag device-specific chunks with `DeviceFamily` and `Capabilities` rather than a free-form custom tag — the system handles upgrades correctly when the user moves to new hardware
- Avoid creating tiny chunks; merge anything under a few MB into a parent

## Querying and driving installs at runtime

Use `XPackage` from the GDK runtime to inspect chunk state and trigger installs:

- `XPackageEnumerateFeatures` — list features available for the installed package
- `XPackageInstallChunks` — request install of one or more chunks; returns an install monitor
- `XPackageEstimateDownloadSize` — show the player how big a feature is before they accept the download
- `XPackageUninstallChunks` — free space by removing optional chunks the player no longer needs

Always check `XPackageGetInstallProgress` before gating gameplay on a chunk; do not assume an install request has completed just because the API returned success.

## Specifier reference

<AccordionGroup>
  <Accordion title="Language specifiers">
    Tag chunks by language code. The console or PC installs only the languages the user has selected. Localized assets not needed for the current language stay on the CDN.

    Best practices:

    - One chunk per language, sized as evenly as possible
    - Include a **default language** chunk that is always installed as a fallback
    - Do not scatter localized strings across per-feature chunks; localised text should live in language chunks
  </Accordion>

  <Accordion title="Device specifiers">
    Tag chunks by device family and hardware capability so players only download the assets their console or PC can render.

    Common patterns:

    | Chunk | Devices |
    | --- | --- |
    | 4K/HDR assets | Xbox One X, Series X, capable PCs |
    | High-detail meshes | Series X, PCs meeting min-spec |
    | Standard assets | All devices |

    Device evaluation is refreshed automatically when a player upgrades hardware or moves a package to a new console.
  </Accordion>

  <Accordion title="Custom tag specifiers">
    Free-form tag strings used when built-in specifiers do not fit. Custom tags let you name a group of chunks for later reference by a feature recipe or a runtime install request. Custom tag names are **not encrypted** — do not use sensitive strings.
  </Accordion>

  <Accordion title="Features and recipes">
    A **feature** is a named, optional group of chunks — for example, a campaign, a raid pack, or a hi-fi audio pack. Recipes map features to the chunks that must install to enable them.

    Runtime API:

    - `XPackageEnumerateFeatures` — list available features
    - `XPackageInstallChunks` — install the chunks backing a feature on demand
    - `XPackageUninstallChunks` — free space by removing an optional feature
  </Accordion>

  <Accordion title="On-demand content (legacy)">
    On-demand tags predate Features. New titles should tag optional content with **Features** instead. Existing titles using on-demand tags continue to work.
  </Accordion>
</AccordionGroup>
