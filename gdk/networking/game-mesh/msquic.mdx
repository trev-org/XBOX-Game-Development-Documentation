[MsQuic](https://github.com/microsoft/msquic) is Microsoft's implementation of the [IETF QUIC](https://datatracker.ietf.org/wg/quic/about/) protocol — cross-platform, written in C, and designed as a general-purpose QUIC library.

QUIC was originally designed to replace "TLS over TCP" scenarios such as HTTP, and evolved into a general-purpose UDP data transport that can multiplex real-time unreliable datagrams and reliable TCP-like streams over a single connection. That makes it a great client/server transport and base for real-time game traffic.

MsQuic is tailored for GDK titles and also runs on Windows Server, Linux, iOS, Android, and macOS. See the [MsQuic API documentation](https://github.com/microsoft/msquic/blob/main/docs/API.md).

## QUIC features

- All packets encrypted; handshake authenticated with TLS 1.3
- Parallel streams of reliable and unreliable application data
- Exchange application data in the first round trip (0-RTT)
- Improved congestion control and loss recovery
- Survives a change in the client's IP address or port
- Stateless load balancing
- Easily extendable for new features and extensions

## MsQuic implementation

Beyond being tailored for GDK titles, MsQuic offers:

- Optimized for client and server
- Optimized for maximal throughput and minimal latency
- Asynchronous IO
- Receive-side scaling (RSS) support
- UDP send/receive coalescing

## Acquiring MsQuic

Use an [official MsQuic release](https://github.com/microsoft/msquic/blob/main/docs/Release.md). Xbox Series X|S support was added in prerelease/1.9; use the latest official release when possible.

All build flavors of a given MsQuic version are compatible with each other. MsQuic aims for backward compatibility across releases — check the release notes for any exceptions.

<Tabs>
  <Tab title="GDK PC titles">
    Use `msquic_windows_x64_Release_openssl`. GDK PC titles run as native x64 Win32 applications, and the OpenSSL build supports every OS version the GDK supports. The Schannel PC build only supports Windows 11\+.
  </Tab>
  <Tab title="GDK console titles">
    Use `msquic_gamecore_console_x64_Release_schannel`. This flavor restricts MsQuic to `WINAPI_PARTITION_GAMES` and links against `XGamePlatform.lib`. Requires XGDK from October 2021 or later. Consoles use Schannel.
  </Tab>
</Tabs>

## Client and server authentication

MsQuic reuses the same authentication and verification paths used for HTTPS to authenticate your server. Follow the best practices in the secure client/server communication guidance for client authentication.

On both sides, use [`ConfigurationLoadCredential`](https://github.com/microsoft/msquic/blob/main/docs/api/ConfigurationLoadCredential.md) with an appropriate [`QUIC_CREDENTIAL_CONFIG`](https://github.com/microsoft/msquic/blob/main/docs/api/QUIC_CREDENTIAL_CONFIG.md) to configure certificates. All default cipher suites are secure, but you must set up validation correctly to establish a secure channel.

<Tabs>
  <Tab title="Server">
    For XSTS token client authentication, specify:

    - `QUIC_CREDENTIAL_FLAG_REQUIRE_CLIENT_AUTHENTICATION`
    - `QUIC_CREDENTIAL_FLAG_INDICATE_CERTIFICATE_RECEIVED`
    - `QUIC_CREDENTIAL_FLAG_NO_CERTIFICATE_VALIDATION`

    When you specify `NO_CERTIFICATE_VALIDATION`, you must validate the client certificate yourself in the [`QUIC_CONNECTION_EVENT_PEER_CERTIFICATE_RECEIVED`](https://github.com/microsoft/msquic/blob/main/docs/api/QUIC_CONNECTION_EVENT.md#quic_connection_event_peer_certificate_received) callback.

    Provide a properly rooted server certificate so clients can authenticate the server as with any HTTPS service.
  </Tab>
  <Tab title="Client">
    **Never** specify `QUIC_CREDENTIAL_FLAG_NO_CERTIFICATE_VALIDATION` on the client — MsQuic's default server validation is the safest option.

    For XSTS client auth, use `QUIC_CREDENTIAL_FLAG_CLIENT` with the certificate generated by your server. Supply it via `QUIC_CREDENTIAL_TYPE_CERTIFICATE_CONTEXT` and use APIs like [`CertCreateContext`](/windows/win32/api/wincrypt/nf-wincrypt-certcreatecontext) to build the context directly from web request response data.
  </Tab>
</Tabs>

## Network initialization

MsQuic does **not** automatically handle [network initialization](/gdk/networking/initialization) for GDK titles. Wait for the network to become initialized after title launch and after each resume before calling [`MsQuicOpenVersion`](https://github.com/microsoft/msquic/blob/main/docs/api/MsQuicOpenVersion.md) or [`MsQuicOpen`](https://github.com/microsoft/msquic/blob/main/docs/api/MsQuicOpen.md).

## Suspend and resume

Register for suspend/resume events with `RegisterAppStateChangeNotification`.

<Steps>
  <Step title="On suspend">
    Close all open streams and close MsQuic.
  </Step>
  <Step title="On resume">
    Wait for network initialization, then reopen MsQuic.
  </Step>
</Steps>

To close all streams quickly within the suspend timeout:

<Steps>
  <Step title="Shut down each stream">
    Call [`StreamShutdown`](https://github.com/microsoft/msquic/blob/main/docs/api/StreamShutdown.md) with `QUIC_STREAM_SHUTDOWN_FLAG_ABORT` and `QUIC_STREAM_SHUTDOWN_FLAG_IMMEDIATE`. This triggers `QUIC_STREAM_EVENT_SHUTDOWN_COMPLETE` immediately.
  </Step>
  <Step title="Close each stream">
    Call [`StreamClose`](https://github.com/microsoft/msquic/blob/main/docs/api/StreamClose.md) after shutdown completes.
  </Step>
  <Step title="Shut down connections">
    Call [`ConnectionShutdown`](https://github.com/microsoft/msquic/blob/main/docs/api/ConnectionShutdown.md) with `QUIC_CONNECTION_SHUTDOWN_FLAG_SILENT`, followed by [`ConnectionClose`](https://github.com/microsoft/msquic/blob/main/docs/api/ConnectionClose.md).
  </Step>
  <Step title="Close outstanding registrations and configurations">
    Call [`RegistrationClose`](https://github.com/microsoft/msquic/blob/main/docs/api/RegistrationClose.md) and [`ConfigurationClose`](https://github.com/microsoft/msquic/blob/main/docs/api/ConfigurationClose.md), then [`MsQuicClose`](https://github.com/microsoft/msquic/blob/main/docs/api/MsQuicClose.md).
  </Step>
</Steps>

## Preferred port

Use the [preferred local UDP multiplayer port](/gdk/networking/game-mesh/preferred-udp-port) for main game traffic in GDK titles. Set it in MsQuic via [`SetParam`](https://github.com/microsoft/msquic/blob/main/docs/api/SetParam.md) with `QUIC_PARAM_CONN_LOCAL_ADDRESS` on a connection handle before calling [`ConnectionStart`](https://github.com/microsoft/msquic/blob/main/docs/api/ConnectionStart.md).

Specify `AF_UNSPEC` for dual-stack IPv4/IPv6 sockets.

```cpp
uint16_t preferredPort;
if (SUCCEEDED(XNetworkingQueryPreferredLocalUdpMultiplayerPort(&preferredPort)))
{
    QUIC_ADDR localAddress = {};
    localAddress.si_family = AF_UNSPEC;
    localAddress.Ipv4.sin_port = htons(preferredPort);

    QUIC_STATUS status = MsQuicCallTable->SetParam(
        MsQuicConnectionHandle,
        QUIC_PARAM_LEVEL_CONNECTION,
        QUIC_PARAM_CONN_LOCAL_ADDRESS,
        sizeof(localAddress),
        &localAddress);
}
```

## Memory considerations

MsQuic's performant implementation enables high bandwidths. As an extension of [Winsock memory considerations](/gdk/networking/game-mesh/winsock#socket-memory-considerations), follow these best practices to minimize kernel memory:

- **Keep callback execution minimal.** MsQuic doesn't use separate threads for protocol execution and upcalls, so any delay in the callback delays the protocol and grows kernel memory usage. Do significant work on your own threads.
- **Manage send buffers efficiently.** See [Send buffering in MsQuic](https://github.com/microsoft/msquic/blob/main/docs/Streams.md#send-buffering).
- **Use asynchronous receives.** See [Receiving in MsQuic](https://github.com/microsoft/msquic/blob/main/docs/Streams.md#receiving). Don't use the partial data acceptance feature in GDK clients — it increases kernel memory usage.
