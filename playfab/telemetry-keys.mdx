**Telemetry Keys** are the lightweight, unauthenticated ingest path for events that don't need to be tied to a specific PlayFab entity at write time. They're the right tool for:

- Boot-time / pre-login metrics ("main menu loaded", "driver version").
- Crash and ANR reports.
- Marketing attribution events from web / campaign landings.
- High-volume gameplay telemetry that doesn't need per-player attribution.

When you need player-attributable events, use **PlayStream** instead (which requires a signed-in entity or a title-secret-authenticated server). Most live titles use both.

## Quickstart

1. In Game Manager → **Data → Telemetry Keys**, create a new key. Give it a descriptive name (`prod_gdk_client`).
2. Copy the key value into your client build. Keep it out of source control; ship it via your build pipeline.
3. From the client, call `EventsAPI.WriteTelemetryEvents` with the key in the `X-TelemetryKey` header (SDKs do this for you if you set the key at init time).
4. Verify ingest by opening **Insights** and running:
   ```kusto
   events
   | where PreciseTimeStamp > ago(15m)
   | where EventName == "main_menu_loaded"
   | take 50
   ```

## Session events

A session ID groups events between app launch and exit (or a timeout). PlayFab automatically emits session-start and session-end events when you configure them on the key. Use sessions to compute:

- Session length distributions.
- Session-scoped funnels ("loaded main menu → hit play").
- Crash rate per session.

## Managing keys

- **Rotate on schedule.** A telemetry key is a low-severity secret but should still rotate on employee changes.
- **One key per surface.** Separate keys for GDK client, mobile, web launcher — easier to disable one without collateral damage.
- **Activate / Deactivate** rather than delete. Deletion loses the event history association if you later need to filter by key.
- **Opt in service events deliberately.** Every service event is a row — don't turn on the whole set on a huge title without checking the volume.

## Throttling and quotas

Telemetry Keys have per-key rate limits and per-title daily quotas that vary by tier. Under sustained overrun PlayFab starts sampling or rejecting. Design your client to:

- Batch events (SDKs batch by default).
- Coalesce duplicate high-frequency events client-side.
- Backoff on 429 rather than retry-storm.

## From ingest to insight

Once events arrive, they're queryable through **Insights** (KQL), exportable via **Data Connections**, and can trigger **Actions & Rules**. Note that a rule keyed on a player entity won't fire from a telemetry event that lacks one — use PlayStream for player-scoped automation.

## Best practices

- **Include a schema version** on every event so you can migrate without breaking existing dashboards.
- **Timestamp with the client's local UTC**, and let PlayFab overwrite with server time for auditable events.
- **Never send PII.** Emails, IP addresses, and free-text chat should be redacted or hashed before ingest.
- **Own your event catalog.** A living doc of every event name \+ property \+ type is invaluable when your dashboards start disagreeing.
