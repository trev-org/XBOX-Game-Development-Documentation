Developer identity is how your team — not your players — signs in to PlayFab. It covers Game Manager access, service-to-service authentication, and the audit trail your ops team relies on.

## Sign in to Game Manager

Game Manager supports two sign-in modes:

- **PlayFab account** — email \+ password with mandatory two-factor authentication (2FA).
- **Microsoft Entra ID (formerly Azure AD)** — recommended for studios of any real size. Enables single sign-on, group-based permissions, and conditional access policies you already run for the rest of Microsoft 365.

AAD sign-in is configured per studio. Once enabled, all developer accounts in that studio must sign in through AAD; local passwords are disabled.

## Two-factor authentication

2FA is enforced for all PlayFab-account developer sign-ins. Supported second factors:

- Authenticator app (TOTP) — Microsoft Authenticator, Google Authenticator, 1Password, etc.
- Email one-time code (fallback).

Studio owners can require 2FA for all members and rotate the requirement.

## Secret key management

Each PlayFab title has one or more **secret keys** used to authenticate server-side (title-authoritative) API calls. Treat them like production database credentials:

- Store secret keys in a secrets manager (Key Vault, AWS Secrets Manager, HashiCorp Vault). Never commit to source control.
- Rotate on a schedule and immediately on any suspected compromise.
- Use **per-key scoping** in Game Manager to limit which API groups each key can call — for example, a build-server key that can only publish content but can't read player data.
- Revoke keys the moment a team member with access leaves the project.

Secret keys live under **Game Manager → Title settings → Secret keys**.

## API access policy

The API Access Policy page in Game Manager lets you narrow which client APIs your title exposes. Disable APIs you don't use — for example, if your title never lets clients write PlayerData directly, disable `UpdateUserData` at the policy level to reduce your attack surface.

## Audit logs

Every change made through Game Manager or an admin API is recorded in the **Audit Log**. Each entry captures who made the change, when, from what IP, and the before/after values. Retention depends on your PlayFab tier.

Use audit logs to:

- Investigate accidental deletes or policy changes.
- Track secret-key creation and rotation.
- Feed a SIEM. The log is exportable as CSV and events are also emitted through Data Connections.

## Studio membership and roles

A PlayFab **studio** is the org-scoped container for one or more titles. Each member of the studio has a role:

- **Owner** — full control including billing and studio-level configuration.
- **Admin** — can manage titles and members but not billing.
- **Developer** — day-to-day access to Game Manager for assigned titles.
- **Custom roles** — combine granular permission bits (recommended for larger studios).

Use custom roles to give QA engineers read-only production access, or to give a live-ops team write access to segments and rules without exposing secret keys.
