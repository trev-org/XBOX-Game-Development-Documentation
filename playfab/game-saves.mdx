**Game Saves** stores a player's save data in PlayFab and syncs it across the devices the player signs in on. It is the recommended save system for cross-platform GDK titles because the same save follows the player between XBOX and Windows, and (with the Steam Deck implementation) between XBOX / Windows and Steam.

## When to use Game Saves

Use Game Saves when any of the following are true:

- Your title ships on more than one platform and you want save state to follow the player.
- Players expect to resume where they left off after switching devices.
- You already use PlayFab for identity or economy — saves complete the picture.

If your title is single-platform and offline-first, XBOX Connected Storage or platform-native save systems may still be simpler.

## Concepts

<CardGroup cols={2}>
  <Card title="Save container" icon="box-archive">

  </Card>

  <Card title="Active device" icon="circle-check">
    Only one device at a time is the authoritative writer for a container. Others read only until the active device changes.
  </Card>

  <Card title="Conflict" icon="triangle-exclamation">

  </Card>

  <Card title="Rollback" icon="clock-rotate-left">
    Restore an older revision of a container from PlayFab's revision history — typically as recovery UI for a corrupted save.

## Onboarding

1. Enable Game Saves in Game Manager → **Player Progression → Game Saves**.
2. Configure your container definitions (name, max size, retention policy, PlayStream event settings).
3. Integrate the Game Saves API into your title (see platform-specific implementations below).
4. Wire up the UI callbacks so players see save / conflict / rollback UI at the right moments.

## Platform implementations

### October 2025 GDK implementation

The **October 2025 GDK** release re-plumbs Game Saves on XBOX and Windows GDK to use the PlayFab Game Saves API directly, replacing older shims. Key changes:

- Direct GDK bindings — no third-party service layer in the critical path.
- Unified conflict / rollback UX with the rest of PlayFab.
- Better cross-generation compatibility (XBOX One ↔ Series X|S).
- New PlayStream events at save-boundary points for analytics and debugging.

If you're on an earlier GDK on an existing title, plan the migration in a dedicated release window — saves are player-visible and any regression is very visible.

### Steam Deck implementation

The **Steam Deck implementation** brings Game Saves to Steam titles on Steam Deck (and any Steam client) using the same PlayFab back end. The integration:

- Signs the player into PlayFab via `LoginWithSteam` on Steam launch.
- Uses the Steam Cloud save format on disk locally, but authoritative state lives in PlayFab.
- Enables cross-shop play — a save that started on XBOX GDK can be resumed on Steam Deck.

Requires linking the player's XBOX and Steam PlayFab identities. See [Identity](/playfab/identity) for the linking flow.

## Account linking

Game Saves is tied to the PlayFab identity, not to a platform account. If a player wants their XBOX save to appear on Steam:

1. On Steam, prompt the player to link their XBOX account.
2. The linked PlayFab account owns the save container.
3. Steam client now sees the same save.

If identities are unlinked, saves diverge from that point.

## Conflict resolution

When two devices race to write, Game Saves stops both, returns both revisions, and calls your **conflict callback**. Your title decides:

- **Take mine** — push the local revision and discard the remote.
- **Take theirs** — discard the local revision and pull the remote.
- **Merge** — build a synthesized revision (recommended for structured save data like loadouts \+ progress \+ settings).
- **Ask the player** — present a UI with previews. Always the safest for player-visible progression.

Emit the resolution as a PlayStream event so you can measure conflict frequency and refine the heuristic.

## Rollback

Every successful write appends a revision. Older revisions are retained per your policy (typically 30 days or last 10 saves). The Rollback API returns a specific historical revision so you can:

- Recover from a corrupted save ("the file is 0 bytes on my machine").
- Recover from a bad game-side migration ("1.2.3 rewrote my save wrong; roll me back to 1.2.2").
- Give players a support-driven undo path.

Rollback is a write — it makes the selected revision the new head.

## Offline mode

If the network is unavailable at the moment of save:

- The write is queued locally.
- Reads return the last-known good state.
- Once connectivity returns, Game Saves reconciles the queue against remote state — which may fire a conflict callback if the remote moved.

Always handle the offline-first path. On console networks in particular, transient disconnects are the norm.

## UI callbacks

Your title must implement the standard UI callbacks:

- **Save in progress** — non-blocking spinner in the corner.
- **Conflict** — modal choose-your-save UI.
- **Rollback available** — optional CTA in the pause menu.
- **Active device changed** — informational toast ("Save is now active on Windows PC").
- **Save failed** — blocking modal with retry.

Spec these with your UX team; they're player-facing and highly scrutinized.

## PlayStream events

Game Saves emits events on every save-boundary transition: begin write, commit, conflict, resolve, rollback, active-device change. Route them into Analytics for dashboards on:

- Save latency percentiles per platform.
- Conflict rate per title version.
- Rollback frequency — a spike after a release usually means a save-format regression.

## Limits

Max container size, max revisions retained, and per-title storage caps are documented in the Game Manager **Limits** page for your title. Design saves to fit comfortably — blobs bloat over live-service lifetimes.

## Best practices

- **Version your save format explicitly.** Include a schema version in every payload; migrate on read.
- **Split containers.** "settings" \+ "progress" \+ "loadouts" is easier to iterate than one monolithic blob.
- **Merge in preference to picking.** A pure "take mine" is a lost session for someone.
- **Instrument.** Save failures are silent player rage. Alert on latency and failure rates in production.
- **Test offline paths in CI.** Simulate no-network at every save site.
