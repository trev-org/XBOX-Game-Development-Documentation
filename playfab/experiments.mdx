Experiments let you test changes on a slice of players and measure the effect on the metrics that matter — D1/D7/D30 retention, ARPU, session length, conversion, or any custom metric you send through PlayStream or Telemetry.

## Concepts

- **Experiment** — a set of two or more variants (one is usually a control) plus enrollment, duration, and metrics.
- **Variant** — a named configuration the client resolves at sign-in ("control", "cheap\_bundle", "expensive\_bundle").
- **Enrollment segment** — the population the experiment applies to. Everyone else is unaffected.
- **Scorecard metrics** — the metrics evaluated automatically for statistical significance.
- **Exclusion group** — a bucket of mutually exclusive experiments so a player can't be in two conflicting tests.
- **Experimentation keys** — title-data-like key/value pairs that vary by variant.

## Design an experiment

1. **Pick a hypothesis and a primary metric.** "Reducing starter bundle price from 999 to 499 will raise Day-3 conversion." The primary metric is Day-3 first-purchase rate.
2. **Choose an enrollment segment.** New installs in the last 24 hours, US region, iOS \+ Android.
3. **Choose variants and split.** control (50%) / test (50%).
4. **Pick scorecard metrics.** Primary \+ guardrails (crash rate, uninstall rate, ARPU) so a win on one metric doesn't hide a regression on another.
5. **Assign an exclusion group.** Anything touching monetization goes in the `monetization` exclusion group.
6. **Set duration.** Long enough for the primary metric to reach the required sample size — the scorecard predicts this before you start.

## Read the variant at runtime

On sign-in the client receives its treatment assignments in the login response. Use `GetTreatmentAssignment` to fetch or refresh:

```cpp
PlayFabClientAPI::GetTreatmentAssignment(request,
    [](const GetTreatmentAssignmentResult& result, void*) {
        for (const auto& v : result.Variables) {
            // e.g. v.Name == "starter_bundle_price", v.Value == "499"
        }
    }, nullptr);
```

Branch on the variables and behave accordingly. Because assignments are deterministic per player, the same player always sees the same variant across sessions.

## Analyze results

The **Experiments scorecard** in Game Manager shows:

- Per-variant means, sample size, and confidence intervals for every scorecard metric.
- Statistical significance vs. control (typically 95%).
- Guardrail deltas so regressions are visible even if the primary metric wins.

For deeper analysis, join the experiment assignment table with your Insights events or with a Data Connection export and slice by any dimension you like.

## Best practices

- **Only one primary metric.** More metrics = more chances for a false positive.
- **Pre-register your minimum detectable effect.** Don't chase a null result.
- **Use guardrails.** A conversion win that raises crash rate is not a win.
- **Stop early only when the scorecard says so.** Peeking without adjustment inflates false positives.
- **Ship the winning variant, then rerun the experiment** to confirm the effect persists after novelty.

## Integration with other PlayFab services

- **Segments** — experiment on any segment; use experiment-assignment as a segment condition to target follow-up messages.
- **Title Data / Experimentation keys** — vary tunables by variant without an app update.
- **CloudScript / Azure Functions** — branch server-side logic on the caller's variant.
- **Insights** — the raw event data underneath the scorecard, queryable with KQL.
