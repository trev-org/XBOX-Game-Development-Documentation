**Data Connections** stream your PlayFab event pipeline out to your own storage, warehouse, or SIEM. Everything ingested through PlayStream and Telemetry Keys, plus service-generated events, can be exported in near real time.

## Supported sinks

## Quickstart with Data Connections

1. In Game Manager → **Data → Data Connections**, click **New connection**.
2. Pick your sink (ADX, Fabric, Blob, Event Hubs, S3, or Kafka).
3. Provide credentials — usually a managed identity or a SAS token; the UI walks you through the specific requirements per sink.
4. Choose which event streams to include: PlayStream (title events), Telemetry Keys, service-generated events, or a subset.
5. Enable **event sampling** and **event partitioning** as needed (below).
6. Activate the connection. Data starts flowing within a minute or two.

## Event sampling

High-volume titles don't always need 100% of events downstream. **Event sampling** lets you keep a percentage (e.g., 10%) of a specific event type. The sample is deterministic per-player so per-user aggregations are still meaningful.

Good candidates for sampling:

- Ultra-frequent gameplay events (`heartbeat`, `frame_stats`).
- Verbose debug events left on in production.

Bad candidates:

- Purchases, grants, or anything a support case might need.
- Session start / end.

## Event partitioning

**Event partitioning** controls how events are laid out in the sink so that queries can scan a smaller slice. For Blob / Data Lake sinks, partition by:

- Date (`year=YYYY/month=MM/day=DD/`) — always start with this.
- Event name.
- Title version.
- Region.

More partitions = smaller queries but more small files. Pick 2–3 partition dimensions; not 6.

## Reconciliation

Always reconcile PlayFab-side event counts with your downstream count. Simple daily job:

1. Query PlayFab Insights for `count() by EventName, day`.
2. Query your warehouse for the same.
3. Alert on any per-event drift above a threshold (say, 1%).

Drift usually means the connection is throttling, credentials expired, or a schema change broke the sink parser.

## Cost considerations

- Data Connections themselves are billed by event volume.
- The sink is billed by its own provider (Azure Storage, S3, ADX cluster hours).
- Sampling and partitioning are the two biggest levers for controlling both.

## Common patterns

- **BI stack**: Data Connection → Fabric RTA → Power BI dashboards.
- **Long-term retention**: Data Connection → Blob (Parquet) → lifecycle-managed to cool / archive.
- **SIEM**: Data Connection → Event Hubs → Sentinel or Splunk.
- **Warehouse**: Data Connection → S3 or Blob → Snowflake / Databricks ingestion.

## Best practices

- **Version your event schema.** Publish a change to the schema doc _before_ the client emits the new field.
- **Namespace event names.** `economy.purchase.completed` beats `purchase` when three teams ship events.
- **Test the pipeline in a dev title first.** Volume mistakes are expensive at production scale.
- **Alert on lag.** If your dashboard is 30 minutes behind, live-ops decisions are made on stale data.
