Any system that grants value to players will be attacked. This page lists the concrete controls PlayFab Economy v2 gives you and the operational patterns that make them work.

## Receipt validation

Every `RedeemXInventoryItems` call in PlayFab validates the receipt against the platform's own service before granting. Additionally PlayFab records the receipt ID and refuses to grant twice for the same receipt. Your responsibilities:

- Do the initial platform-side verification **on your back end**, not the client, before calling PlayFab.
- Log the receipt ID, PlayFab entity ID, and IP with every redemption call so you can investigate disputes.
- Watch the reject-rate on `Receipt*` events. A sudden spike is usually an attacker enumerating receipt IDs.

## Redemption limits

Redemption code batches support per-code and per-player limits. Configure them in Game Manager → **Economy → Marketplace redemption**:

- **Uses per code** — usually `1` for individual codes, higher for shared campaign codes.
- **Uses per player** — prevent one player from redeeming the same code from multiple accounts.
- **Redemption window** — start / end dates for time-limited campaigns.
- **Segment restriction** — only players in segment X can redeem.

For shared campaign codes (creator promo drops, in-video codes), always couple them with a per-player limit — otherwise a single account will drain the pool.

## Server-authoritative grants

Any grant that changes economic value must originate on a trusted surface:

- **CloudScript / Azure Functions** — for cross-cutting server logic. See [CloudScript & Azure Functions](/playfab/cloudscript).
- **PlayFab Multiplayer Server** with the title secret — for gameplay-driven grants inside a session.
- **Your own back end** with the title secret — for external systems.

Disable client access to admin-style APIs (`GrantItemsToUser`, `UpdatePlayerStatistics` for server-scored stats) in Game Manager → **API access policy**.

## Rate limiting and throttles

PlayFab enforces per-title and per-player rate limits on every API. Layer your own budgets on top:

- Cap `RedeemInventoryItems` per player per hour in CloudScript.
- Cap UGC uploads per creator per day.
- Cap Cross-title codes per player-lifetime.

When a limit is exceeded, return a friendly error and log a segment tag so the abuse team can investigate.

## Anti-cheat signals

Join PlayFab data with any anti-cheat provider you use (BattlEye, EAC, or a custom system):

- Ban a player in your anti-cheat system → tag their PlayFab account and add to a `banned` segment.
- Segment-condition every grant to exclude banned players.
- Use an Actions & Rule to freeze the account's inventory immediately on ban.

## Fraud analytics

Every redemption, grant, and moderation decision emits a PlayStream event. Build an Insights dashboard tracking:

- Reject rate by error code, by hour.
- Top redeeming players by 24h grant value.
- New-install → first-purchase in less than N minutes (chargeback proxy).
- Codes redeemed per unique IP / device fingerprint.

Alert on step-changes and hand off to a human review workflow.

## UGC-specific controls

- Content-safety scan every upload (image \+ text).
- Rate-limit ingest per creator.
- Track a creator quality score; auto-throttle low-score creators.
- Cascade take-downs — removing an item should refund purchases according to your policy.

More in [User-Generated Content (UGC)](/playfab/ugc).

## Incident response

When you discover an active exploit:

1. Disable the vulnerable code batch or catalog item in Game Manager (immediate, no deploy needed).
2. Freeze affected accounts (add to `investigation` segment; block grants).
3. Pull the raw event stream for the exploit window from a Data Connection.
4. Reverse ill-gotten grants via CloudScript (`SubtractInventoryItems` / rebalance currency).
5. Post-mortem — what was the missing control? Add it to your controls list here.
