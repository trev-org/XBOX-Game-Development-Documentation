A **marketplace integration** connects a PlayFab catalog item to a real-world storefront so purchases made outside your game (Microsoft Store, Steam, App Store, Google Play, publisher website) fulfill inside your game. **Marketplace redemption** covers the code-based side: publisher-issued codes, retail cards, promo drops, and cross-title reward codes.

## Supported marketplace integrations

| Marketplace | Typical use |
| --- | --- |
| Microsoft Store | XBOX & Windows GDK titles — IAP and DLC fulfillment |
| Steam | Windows titles distributed on Steam |
| Apple App Store | iOS / macOS |
| Google Play | Android |
| Publisher web store | External purchase pages, subscription upgrades |

Each integration follows the same pattern: your title (or your web store) verifies the platform receipt with the platform's own APIs, then hands the verified receipt to PlayFab. PlayFab checks it hasn't been used before, resolves the mapped catalog entry, and grants inventory.

## Integration flow (using Microsoft Store as the example)

<Steps>
  <Step title="Player buys through the platform">
    Player completes checkout in the Microsoft Store UI (or from XStore in-game). Platform returns a receipt to the client.
  </Step>
  <Step title="Client sends receipt to a trusted back end">
    Client posts the receipt to your game server, CloudScript, or Azure Function. Never trust the client to grant items itself.
  </Step>
  <Step title="Back end verifies with Microsoft">
    Back end calls `Microsoft.StoreServices.CollectionsService` to confirm the receipt is legitimate and belongs to the reported user.
  </Step>
  <Step title="Back end forwards to PlayFab">
    Back end calls `Economy.RedeemMicrosoftStoreInventoryItems`. PlayFab records the receipt to prevent replays and grants the mapped catalog items.
  </Step>
  <Step title="Consumables reported fulfilled">
    For consumables, call `XStoreReportConsumableFulfillment` so the platform knows the entitlement was used. Otherwise the client will keep seeing it as unfulfilled.
  </Step>
</Steps>

See [Microsoft Store integration](/playfab/microsoft-store) for the full XStore \+ PlayFab code.

## Marketplace redemption (codes)

Redemption codes are the workhorse of publisher marketing:

- **Retail cards** — \$10 gift cards at a retail chain that grant currency in your title.
- **Beta / crossover keys** — access codes shipped by email or partner platform.
- **Promo drops** — codes distributed at events, in creator videos, or through partner storefronts.

In Game Manager → **Economy → Marketplace redemption**, create a code batch bound to one or more catalog items. PlayFab generates the codes and tracks:

- Total issued vs. redeemed.
- Per-code redemption timestamp and player.
- Optional per-code and per-player redemption limits.

Redeem from the client with `RedeemInventoryItems` — same server-authoritative pattern as any other grant, so ideally the actual redemption call is proxied through CloudScript to enforce anti-abuse rules.

## Error handling

Common failure modes and what they mean:

| Error | Cause | Handling |
| --- | --- | --- |
| `ItemNotOwned` | Platform says the user doesn't own the SKU | Client bug or fraud attempt — log and reject |
| `ItemAlreadyRedeemed` | Receipt or code has been used | Return silently, don't double-grant |
| `ItemNotFound` | Catalog mapping missing | Fix the catalog mapping in Game Manager |
| `InvalidReceipt` | Signature check failed | Log for fraud analysis |
| `CodeExpired` / `CodeDisabled` | Code batch is past its window or was killed | Show a friendly message |

Surface actionable errors to support tooling — receipt IDs, timestamps, catalog IDs — so your CX team can resolve player-side disputes fast.

## Best practices

- **Always verify server-side.** The client can be modified; platform receipts must be validated by a trusted back end.
- **Idempotent grants.** Even if a receipt is submitted twice, PlayFab will not double-grant — but your client should tolerate the same response either way.
- **Consumable fulfillment reporting** is required on Microsoft Store to prevent the platform from re-serving a consumable as unfulfilled.
- **Reconcile daily** — export PlayFab redemption events through a Data Connection and reconcile against platform receipt tables to catch mismatches.
